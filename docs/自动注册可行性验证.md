# 两阶段自动注册：受限可行性验证

本实验验证“扫描具体类型 → 生成 Rust 注册源码 → 第二轮编入原 crate”，不是修改 rustc 的单态化收集器，也不是按正则猜测函数地址。核心 runtime、proc-macro 和 GDB 协议保持不变。

## 结论与范围

主链路已在本机跑通：无手动 `register_type!` 的 HashMap、IndexMap、仅实现 Debug 的自有类型可以通过 `dbgvis print` 输出；debug 与 release/LTO 的真实 GDB 调用均已验证。完整可重复的编译与 GDB 验证命令见下文。

这是 **严格模式的实验后端**，尚不能代替所有手动登记。第一轮只按根 trait 筛选，第二轮是最终入口可编译性验证；不支持自动剔除导致单态化失败的候选。依赖库已有同类型根登记会按生命周期擦除后的具体类型 TypeId 合并；同名但身份不同的登记在 enable 时拒绝。不得作为“全程序自动发现、永不破坏原构建”的产品承诺。

## 使用

要求 Linux x86_64、Python 3、GDB、安装了 rustc-dev 的以下确切编译器：

```text
rustc 1.99.0-nightly (12c36e253 2026-08-10)
```

build.py 和 wrapper 都检查版本；这不是对浮动 nightly 的兼容承诺。工具作为独立实验放在 tools/auto-register，不加入 Cargo workspace，不给核心 crate 添加 rustc_private 依赖。构建 driver 直接调用 rustc，动态库查找使用编译产物的 rpath。

`tools/auto-register/Cargo.toml` 是独立 nested workspace，并声明 `[package.metadata.rust-analyzer] rustc_private = true`。VS Code 的 `.vscode/settings.json` 将主 workspace 和该工具分别作为 linked project；因此 RA 可索引 `rustc_ast`、`rustc_middle` 等 rustc-dev crate，不会把 driver 拉入主 workspace。`RUSTC_BOOTSTRAP=1` 仅提供给 RA/Cargo 检查会话，driver 的正式构建仍由 `build.py` 锁定 toolchain。可从 Command Palette 运行 `dbgvis: build auto-register driver`、`dbgvis: check auto-register driver` 和 `dbgvis: run auto-register contracts`。

在仓库根目录执行：

```sh
python3 tools/auto-register/build.py
DBGVIS_AUTO_CRATE=auto_poc \
RUSTC_WORKSPACE_WRAPPER="$PWD/tools/auto-register/wrapper.py" \
cargo build --offline --example auto_poc

rust-gdb -q -nx \
  -iex "add-auto-load-safe-path $PWD/target/debug/examples/auto_poc" \
  target/debug/examples/auto_poc
```

```text
break auto_poc::checkpoint
run
up
dbgvis print map
dbgvis print ordered
dbgvis print debug_only
```

预期分别为：

```text
{7: [Some(Point { x: 42 })]}
{1: "one"}
DebugOnly { count: 9 }
```

examples/auto_poc.rs 不包含容器登记，map 也不是已 derive 的 struct 字段。Point 没有 Debug，证明 HashMap 内确实走 Visualize 递归。IndexMap 则复用自身 Debug，不代表实现了第三方容器元素级 Visualize 适配。

普通 `cargo build --example auto_poc` 仍可构建运行，但不会自动登记这些根；必须启用 wrapper。消费程序仍需依赖 dbgvis 并调用 enable。DBGVIS_AUTO_CRATE 是 rustc 的 crate-name，首版只允许选中一个 bin/example；其他编译请求原样转发。

## 实现方式

1. wrapper 在 Cargo 的一次目标编译请求内启动两个独立 driver 进程。扫描轮移除正式输出/增量目录，使用临时目录，after_analysis 后停止，不执行 LLVM codegen 或链接。
2. driver 查询具体 mono instances，读取本 crate 函数 MIR 的用户变量调试记录，并代入泛型实参。处理常量/ZST 和复合变量碎片，过滤宏展开来源、内联来源及登记辅助函数。不承诺覆盖优化后丢失的变量信息。
3. 从 crate 根和已加载直接依赖的公开 module children 建立 DefId → 可访问源码路径映射。依赖别名根据实际 --extern 文件匹配；绝不将诊断类型字符串直接拼成 Rust 源码。
4. 递归渲染基础类型、元组、数组及可访问 ADT 的具体参数。只有尾部 type 默认参数与实际参数相等时才省略；const 当前限可转换为目标 usize 的值。含生命周期的类型生成单一 `'a` generic alias，并由 `#[dbgvis::register]` 生成 formatter/anchor；匿名、不透明或无大小类型仍报告 SKIP。顶层引用临时变量跳过，避免把 `&T` 的无条件 Visualize 实现误当成 T 可格式化。
5. 读取当前 crate 已生成 typed anchor 的实际字段类型，排除本地已有登记；这是依赖现有宏命名约定的实验实现，不是稳定的登记元数据协议。
6. 根类型满足 Visualize、Debug 或 Display 后生成 register_type!，保留当前 auto 优先级。候选表按源码表达式排序，候选数量有 4096 上限；原 runtime 仍检查包含已有根的总数。
7. 第二轮通过 after_crate_root_parsing 注入根子模块和 include!。宏展开、函数实例化、anchor/linkme 和 GDB 分发全部复用现有实现。

生成物位于 target/auto-register/plans/<crate>-<编译单元散列>/：

- register.rs：第二轮实际编入的 Rust 源码。
- register.tsv：CANDIDATE / EXISTING / SKIP 与诊断类型、原因。
- invocations.log：真实 wrapper 扫描调用记录，用于区分执行与 Cargo 缓存日志重放。

源码内容不变时不改写生成文件。正式 dep-info 跟踪生成文件、工具源码和启用环境变量。首次生成 include 文件可能导致下一次构建再运行一轮，随后应收敛为 fresh；测试检查真实调用记录，而不是只看 Cargo 会重放的 stderr。扫描不读取上一轮生成文件，不将 formatter 辅助类型不断加入候选。

## 验证命令与判据

```sh
# 编译契约、baseline/负向测试、auto_poc/demo debug 与 LTO 构建/运行
python3 tools/auto-register/test.py

# 再加实际 GDB 断点、输出、调用次数、anchor 和进程正常退出断言
python3 tools/auto-register/test.py --gdb
```

测试运行时在系统临时目录生成消费项目（包括用于验证跨库重复登记边界的库），结束后清理；不向 crates 或 tests/fixtures 添加样板库。

| 验证项 | 判据 |
| --- | --- |
| HashMap、IndexMap、DebugOnly 无手动登记 | debug/LTO 中实际 GDB 输出与调用次数一致 |
| 依赖重命名 | 生成 ::dv、::idx 路径且构建、运行成功 |
| 泛型函数局部变量 | generic::<u16> 的 Vec<u16> 出现在计划中 |
| const 泛型 | Packet<u8, 17> 生成并通过两种 profile 构建 |
| 本地 derive / 显式 Display 根 | 不重复登记，保留原根配置，enable 正常执行 |
| 私有模块、函数局部类型 | 生成 SKIP 原因而非猜测可用路径 |
| `IndexMap<&str, ...>`、借用泛型 alias | 生成 `'a` alias，debug/LTO 中通过 GDB 输出 |
| 普通 NoFormat | 根 trait 不满足，跳过 |
| Vec<NoFormat> | baseline 成功；扫描通过；第二轮 E0080，记录严格模式限制 |
| 依赖库已登记 u64 | baseline 与自动模式均成功运行，runtime 合并重复根 |
| 增量行为 | 允许首次预热；之后无实际扫描，生成源码 mtime 不变 |
| 修改业务类型 | 重新发现 Vec<u128>；移除后计划不残留 |

标记：AUTO_COMPILER_CONTRACTS_OK、AUTO_STRICT_FAILURE_CONFIRMED、AUTO_CROSS_CRATE_DEDUP_OK、AUTO_GDB_OK（debug/LTO 各一次）、AUTO_POC_SUITE_OK。负向标记是已验证的限制，不是对应能力已经实现。

本轮验收：`python3 tools/auto-register/test.py --gdb` 已完整通过上述断言，GDB 为 17.1。另已通过 `cargo fmt --all -- --check`、独立 driver 的 rustfmt 检查、`cargo clippy --offline --workspace --all-targets --all-features -- -D warnings` 和 `cargo test --offline --workspace --all-features`。三个核心 crate 无源代码变更。

## 尚未解决的产品化问题

- **可编译性过滤**：Vec<T> 的 Visualize 实现不约束 T，trait 查询无法证明叶子格式化有效。需要能力协议或隔离编译探测，不能拿 cargo check 代替。
- **跨库去重与配置**：同名根只有生命周期擦除后的具体类型 TypeId 一致才合并能力和函数指针，size/align 作附加检查；同名不同身份或不一致形状均拒绝，跨版本 runtime 表也不自动合并。正式方案仍需要可查询登记元数据和更明确的模式优先级。
- **退出语义**：现有 no_register 仅关闭 derive 登记；实验 driver 不把它解释为全局禁止自动登记。尚无逐类型排除配置，暂勿用于依赖该退出行为的工程。
- **作用域与可命名性**：没有私有模块/块级注入，没有传递依赖路径合成、类型别名搜索或所有 const 形式。根路径遍历还保守排除下划线开头的名字。生命周期 alias 目前统一使用一个 `'a`，若类型的 trait 实现依赖多个不等生命周期关系，第二轮会由 Rust 编译器拒绝。
- **覆盖率**：只处理当前目标本地函数的可见 MIR 调试变量，未扫描所有依赖、标准库非泛型函数或宏生成变量；闭包内部未专项验收，已内联来源被过滤。不是全程序类型反射。
- **缓存与发行**：仅验证本地 Cargo 普通增量路径；sccache、交叉编译、并行多目标、no_std、通用 cargo-dbgvis 安装/升级仍未验收。不修改 ~/.cargo 或 ~/.gdbinit。

后续优先顺序：先定义登记/能力元数据及自动注册退出语义，再实现安全的候选过滤；最后扩展作用域和安装体验。不要把正则符号查找加入调用安全链。
