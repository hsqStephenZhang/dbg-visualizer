# 两阶段自动注册：受限可行性验证

本实验验证“扫描具体类型 → 生成 Rust 注册源码 → 第二轮编入原 crate”，不是修改 rustc 的单态化收集器，也不是按正则猜测函数地址。核心 runtime、proc-macro 和 GDB 协议保持不变。

## 结论与范围

主链路已在本机跑通：无手动 `register_type!` 的 HashMap、IndexMap、仅实现 Debug 的自有类型可以通过 `dbgvis print` 输出；debug 与 release/LTO 的真实 GDB 调用均已验证。完整可重复的编译与 GDB 验证命令见下文。

这是 **严格模式的实验后端**，尚不能代替所有手动登记。第一轮只按根 trait 筛选，第二轮是最终入口可编译性验证；不支持自动剔除导致单态化失败的候选。依赖库已有同类型根登记会按生命周期擦除后的具体类型 TypeId 合并；同名但身份不同的登记在 enable 时拒绝。不得作为“全程序自动发现、永不破坏原构建”的产品承诺。

## 使用

要求 Linux x86_64、Python 3、GDB、安装了 rustc-dev 的以下确切编译器：

```text
rustc 1.99.0-nightly (12c36e253 2026-08-10)
```

`cargo xtask driver` 和 wrapper 都检查版本；这不是对浮动 nightly 的兼容承诺。工具作为独立实验放在 tools/auto-register，不加入 Cargo workspace，不给核心 crate 添加 rustc_private 依赖。构建 driver 直接调用 rustc，动态库查找使用编译产物的 rpath。

`tools/auto-register/Cargo.toml` 是独立 nested workspace，并声明 `[package.metadata.rust-analyzer] rustc_private = true`。VS Code 的 `.vscode/settings.json` 将主 workspace 和该工具分别作为 linked project；因此 RA 可索引 `rustc_ast`、`rustc_middle` 等 rustc-dev crate，不会把 driver 拉入主 workspace。`RUSTC_BOOTSTRAP=1` 仅提供给 RA/Cargo 检查会话，driver 的正式构建仍由 `cargo xtask driver` 锁定 toolchain。可从 Command Palette 运行 `dbgvis: build auto-register driver`、`dbgvis: check auto-register driver` 和 `dbgvis: run auto-register contracts`。

在仓库根目录执行：

```sh
cargo xtask driver
DBGVIS_AUTO_CRATE=auto_poc \
RUSTC_WORKSPACE_WRAPPER="$PWD/tools/auto-register/wrapper.py" \
cargo build --offline --example auto_poc

rust-gdb -q -nx \
  -iex "add-auto-load-safe-path $PWD/target/debug/examples/auto_poc" \
  target/debug/examples/auto_poc
```

```text
break auto_poc::checkpoint
run
up
dbgvis print map
dbgvis print ordered
dbgvis print debug_only
```

预期分别为：

```text
{7: [Some(Point { x: 42 })]}
{1: "one"}
DebugOnly { count: 9 }
```

examples/auto_poc.rs 不包含容器登记，map 也不是已 derive 的 struct 字段。Point 没有 Debug，证明 HashMap 内确实走 Visualize 递归。IndexMap 则复用自身 Debug，不代表实现了第三方容器元素级 Visualize 适配。

普通 `cargo build --example auto_poc` 仍可构建运行，但不会自动登记这些根；必须启用 wrapper。消费程序仍需依赖 dbgvis 并调用 enable。DBGVIS_AUTO_CRATE 是 rustc 的 crate-name，首版只允许选中一个 bin/example；其他编译请求原样转发。

## 实现方式

1. wrapper 在 Cargo 的一次目标编译请求内启动两个独立 driver 进程。扫描轮移除正式输出/增量目录，使用临时目录，after_analysis 后停止，不执行 LLVM codegen 或链接。
2. driver 查询具体 mono instances，读取本 crate 函数 MIR 的用户变量调试记录，并代入泛型实参。处理常量/ZST 和复合变量碎片，过滤宏展开来源、内联来源及登记辅助函数。不承诺覆盖优化后丢失的变量信息。
3. 从 crate 根和已加载直接依赖的公开 module children 建立 DefId → 可访问源码路径映射。依赖别名根据实际 --extern 文件匹配；绝不将诊断类型字符串直接拼成 Rust 源码。
4. 递归渲染基础类型、元组、数组及可访问 ADT 的具体参数。只有尾部 type 默认参数与实际参数相等时才省略；const 当前限可转换为目标 usize 的值。含生命周期的类型生成单一 `'a` generic alias，并由 `#[dbgvis::register]` 生成 formatter/anchor；匿名、不透明或无大小类型仍报告 SKIP。顶层引用临时变量跳过，避免把 `&T` 的无条件 Visualize 实现误当成 T 可格式化。
5. 读取当前 crate 已生成 typed anchor 的实际字段类型，排除本地已有登记；这是依赖现有宏命名约定的实验实现，不是稳定的登记元数据协议。
6. 根类型满足 Visualize、Debug 或 Display 后生成 register_type!，保留当前 auto 优先级。候选表按源码表达式排序，候选数量有 4096 上限；原 runtime 仍检查包含已有根的总数。
7. 第二轮通过 after_crate_root_parsing 注入根子模块和 include!。宏展开、函数实例化、anchor/linkme 和 GDB 分发全部复用现有实现。

生成物位于 target/auto-register/plans/<crate>-<编译单元散列>/：

- register.rs：第二轮实际编入的 Rust 源码。
- register.tsv：CANDIDATE / EXISTING / SKIP 与诊断类型、原因。
- invocations.log：真实 wrapper 扫描调用记录，用于区分执行与 Cargo 缓存日志重放。

源码内容不变时不改写生成文件。正式 dep-info 跟踪生成文件、工具源码和启用环境变量。首次生成 include 文件可能导致下一次构建再运行一轮，随后应收敛为 fresh；测试检查真实调用记录，而不是只看 Cargo 会重放的 stderr。扫描不读取上一轮生成文件，不将 formatter 辅助类型不断加入候选。

设置 `DBGVIS_AUTO_CRATE` 后，wrapper 经过的实际 workspace 编译（包括透传的库、build script 和 proc-macro）统一通过 driver 的 `Config::track_state`，在 rustc dep-info 中记录 `DBGVIS_AUTO_CRATE`、`DBGVIS_SCAN_DEPS` 的原始值（包括未设置状态）及工具源码依赖。透传模式不扫描、不注入登记；Cargo 的编译器探测仍直接交给 rustc。这样切换扫描开关时，库会重新编译以增加或移除 MIR 编码，最终可执行文件也会重新生成登记，不需要更换 target 目录。已有旧版 wrapper 产物未记录这些依赖，升级后应先清理一次消费项目的构建缓存，再验证开关切换。

### 可见性矩阵的实际结果

测试生成独立 `.rs` 模块文件，组合根子模块 `mod`/`pub mod`、`fn`/`pub fn` 与类型私有/`pub(super)`/`pub(crate)`/`pub`，再覆盖嵌套模块、re-export、私有方法、私有泛型函数和函数局部类型。类型字段全部保持私有。使用 `#[inline(never)]` 和断点前后的 `black_box(&value)` 保留被测函数与变量；这不承诺任意优化后变量都能被发现或寻址。

| 场景 | driver 行为 / GDB 结果 |
| --- | --- |
| 私有根子模块 + 私有函数 + 私有 Debug 类型 | 发现 T 和 Vec<T>，因根作用域不可引用而 SKIP；打印拒绝且不调用目标 formatter |
| 私有根子模块 + 私有函数 + pub(crate)/pub 类型 | 自动登记 T 和 Vec<T>，两者正常输出；不要求字段公开 |
| 根子模块内 pub(super) 类型 | 可见范围到达 crate 根，可以自动登记 |
| crate 根私有类型 + 私有函数 | 可自动登记；和子模块内的私有类型不同 |
| 多层嵌套的私有模块、类型 | 路径任一段对根不可访问就 SKIP；pub(super) 只有覆盖到根时才足够 |
| 私有嵌套模块通过 pub(crate) use 暴露类型 | 使用可访问的 re-export 路径登记 |
| 私有方法、私有泛型函数的具体实例 | 可以扫描并登记可访问的具体类型 |
| 函数内声明的 Debug 类型 | 发现但无法从根命名，T 和 Vec<T> 均 SKIP |
| 私有/函数局部类型直接 derive Visualize | driver 仍因路径限制 SKIP，但宏已在原作用域登记 T，所以 T 能打印；Vec<T> 不会因此自动成为根 |
| 未调用的私有函数、同包 src/lib.rs 的私有函数 | 本测试不产生候选，后者属于另一个 crate；即使类型公开也不自动扫描其函数体 |

debug/LTO 均验证：可打印根每次只调用一次 dispatcher；被跳过且没有独立登记的根不调用 dispatcher。可见性矩阵已接入 `cargo xtask autoregister` 总入口，无 `--gdb` 时仍验证注册计划与两种构建的实际运行。

## 依赖库扫描（`DBGVIS_SCAN_DEPS`，默认关闭）

非泛型函数在自己的 crate 里 codegen，不会出现在可执行目标的 mono item 集合中，因此库里的局部变量类型默认不可见。对「逻辑在 lib、main 只是入口」的常见布局，这会让自动登记几乎扫不到东西——例如 regex 教学项目的 `lesson3`，只扫 bin 时得到 2 个根，开启依赖扫描后是 31 个，`compile::OpCode` 才进入登记。

实现方式：wrapper 给经过它的 workspace 库加 `-Zalways-encode-mir` 并记录 crate 名，再把「要扫哪些 crate」以正则列表交给 driver（用户设了 `DBGVIS_SCAN_CRATES` 就原样转交，否则是记录下来的库名转义后的形式）；driver 对 `tcx.crates` 逐个全匹配，命中的读 MIR。枚举覆盖三类：模块树里的自由函数、类型的固有方法，以及整个 crate 的 trait 实现（`impl Trait for Type` 既不是模块子节点，也无法从被实现的类型到达，必须按 crate 单独枚举）。判定「非泛型」只看类型和 const 参数，生命周期不算——`Instance::mono` 会擦除它们，若要求完全无泛型参数，带早绑定生命周期的 impl 方法会被整体漏掉。名单是显式的而不是「MIR 可用即扫」——发行版的 std/core 同样编码了 MIR，实测有 6683 个非泛型 std 函数可读，按可用性过滤会把整个标准库的局部变量变成根。

开关由 wrapper 读取的环境变量控制，默认关闭：

```sh
cargo build                     # 只扫可执行目标自身，不加 -Zalways-encode-mir
DBGVIS_SCAN_DEPS=1 cargo build  # 同时扫描 workspace 依赖库
```

也可以写进消费项目的 `.cargo/config.toml` 的 `[env]` 一节。

`DBGVIS_SCAN_CRATES` 决定扫**哪些** crate：逗号切分，每段是一个正则，对整个 crate 名做全匹配（下划线形式，`regex` 只选 `regex`，`regex.*` 才连带 `regex_syntax`）。设了它就隐含开启扫描，不再需要 `DBGVIS_SCAN_DEPS=1`；不设时 `DBGVIS_SCAN_DEPS=1` 等价于「全部 workspace 库」。

```sh
DBGVIS_SCAN_CRATES='mylib,regex.*' cargo build
```

匹配不到任何可扫描 crate 的模式会在 stderr 报出，非法正则直接失败并指出是哪一段。两类 crate 无论模式如何都不会扫：sysroot 里的（发行版 std/core 也编码 MIR，实测 6683 个非泛型函数可读，扫进去会把整个标准库的局部变量变成根）和 dbgvis 自身（`dbgvis_runtime` 里有 `Root` 这类故意不可格式化的局部变量，strict 模式必炸）。wrapper 只给 workspace 库加 `-Zalways-encode-mir`，所以一个 registry crate 即使被模式命中，默认也只有 `#[inline]`/泛型函数带 MIR——以 regex-syntax 0.8.11 实测，直接扫得到 15 个根，保留 MIR 后是 51 个。要扫 registry crate 不必把它搬进 workspace，把 flag 交给 cargo 即可，两种写法：

```toml
# 定向：只给目标包（nightly cargo，需在 Cargo.toml 顶部声明 cargo-features）
cargo-features = ["profile-rustflags"]
[profile.dev.package.regex-syntax]
rustflags = ["-Zalways-encode-mir"]
```

```sh
# 全图：省事，但整个依赖图的 rlib 都会变大
RUSTFLAGS=-Zalways-encode-mir cargo build
```

两者得到的根集合完全一致；定向写法下其余 crate 的 rlib 大小不变，regex-syntax 自身增大约 3.8%。wrapper 检测到参数里已有该 flag 时不会重复添加，cargo 也会把 rustflags 计入 fingerprint。

间接依赖也能扫。生成的登记代码要从 crate 根写出类型路径，而 cargo 只给直接依赖传 `--extern`，间接 crate 不在可执行目标的 extern prelude 里——实测经 `regex` 间接引入 `regex_automata` 并扫它：170 个类型有 MIR，0 个能登记，155 个报 `type is not accessible/nameable from root`。现在 driver 在扫描阶段把「选中但非直接」的 crate 连同 rlib 路径写进计划目录（`register.externs`），wrapper 在编译生成登记的那一次调用里补 `--extern <name>=<rlib>`。crate 本来就已链接，这只是让它的名字可用；stderr 会打出 `exposing indirect dependency ... via --extern`。两种情况不会自动暴露而是提示交给用户：同名多版本同时被链接，或与某个直接依赖的别名撞名（占用名按 cargo 传的全部 `--extern` 收集，声明了但源码没用到的依赖也算，否则会多出第二个 `--extern` 而报 E0464）。库名是关键字时（如 `[lib] name = "async"`）路径根按原始标识符生成 `::r#async`，交给 `--extern` 的名字保持原样。

默认关闭是因为代价真实存在：

- `-Zalways-encode-mir` 会增大 workspace 库的 rlib 并拖慢构建。
- 候选数量显著上升，strict 模式的失败面随之扩大：库里任意一个「元素不可格式化的容器局部变量」都会让最终构建失败，即使调试时根本不看它。
- 只覆盖 workspace 成员：`RUSTC_WORKSPACE_WRAPPER` 不作用于 registry 依赖，所以第三方库不在范围内。
- 扫描范围按定义所属 crate 判断，而不是按 re-export 路径判断：模块、函数、类型及固有方法都检查 `DefId.krate`。选中库 re-export 的外部函数/类型不会带入外部函数局部变量；选中库自身的 re-export 仍受支持，外部类型作为可执行目标自身的局部变量出现时也仍可登记。
- 名单文件写在 `target/auto-register/scan/<crate>/`。可执行目标未实际链接的名字匹配不到任何 crate，因此旧会话遗留的条目不会扩大扫描范围。

`cargo xtask autoregister` 包含两组回归验收：同一 target 目录内 `DBGVIS_SCAN_DEPS=0 → 1 → 0` 的登记变化与缓存收敛；以及 workspace 库 re-export workspace 外依赖的函数、模块、struct/enum/union 固有方法时不会越界扫描。

## 尚未解决的产品化问题

- **可编译性过滤**：Vec<T> 的 Visualize 实现不约束 T，trait 查询无法证明叶子格式化有效。需要能力协议或隔离编译探测，不能拿 cargo check 代替。
- **跨库去重与配置**：同名根只有生命周期擦除后的具体类型 TypeId 一致才合并能力和函数指针，size/align 作附加检查；同名不同身份或不一致形状均拒绝，跨版本 runtime 表也不自动合并。正式方案仍需要可查询登记元数据和更明确的模式优先级。
- **退出语义**：现有 no_register 仅关闭 derive 登记；实验 driver 不把它解释为全局禁止自动登记。尚无逐类型排除配置，暂勿用于依赖该退出行为的工程。
- **作用域与可命名性**：没有私有模块/块级注入，没有传递依赖路径合成、类型别名搜索或所有 const 形式。根路径遍历还保守排除下划线开头的名字。生命周期 alias 目前统一使用一个 `'a`，若类型的 trait 实现依赖多个不等生命周期关系，第二轮会由 Rust 编译器拒绝。
- **覆盖率**：处理当前目标本地函数的可见 MIR 调试变量，以及显式开启 `DBGVIS_SCAN_DEPS=1` 时 workspace 依赖库中非泛型函数的同类变量。未扫描标准库、registry 依赖或宏生成变量；闭包内部未专项验收，已内联来源被过滤。不是全程序类型反射。
- **缓存与发行**：仅验证本地 Cargo 普通增量路径；sccache、交叉编译、并行多目标、no_std、通用 cargo-dbgvis 安装/升级仍未验收。不修改 ~/.cargo 或 ~/.gdbinit。

后续优先顺序：先定义登记/能力元数据及自动注册退出语义，再实现安全的候选过滤；最后扩展作用域和安装体验。不要把正则符号查找加入调用安全链。
