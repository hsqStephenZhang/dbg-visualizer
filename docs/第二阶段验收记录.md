# 第二阶段核心验收记录

日期：2026-09-10；2026-09-11 更新 linkme 自动收集验收。路线：**nightly specialization、GDB 优先、移除 v1**。记录的是本地实际结果，不代表所有计划项完成，也不代表远端 CI 或 crates.io 发布已完成。

演示入口现为 examples/demo.rs：自有类型全部直接 derive Visualize，无 feature gate；运行 `cargo build --example demo`。仓库中的 a/b/c fixture 已删除，workspace 仅有三个核心 crate；tests/compiler/run.py 在临时目录生成 a/b/c 及消费项目，保留启用/关闭和 debug/LTO 验证，结束后自动清理源码。

## 1. 已交付核心

- `dbgvis` facade、`dbgvis-macros`、nightly `visualizer-runtime`。
- derive、字段 skip/rename/via/transparent/bound、具体根注册、main/enable。
- 非泛型 derive 自动根登记，no_register 可关闭；register 属性、register_type!；linkme 跨 crate 收集工厂，无参数 enable/main；集中式 visualizers 入口删除。
- Visualize > Debug > Display 的泛型自动选择；失败不重试其他能力。
- 泛型容器、借用、const 参数和 ZST 策略；独立 a/b/c 递归组合。
- TypeId 标记、typed anchor、类型固定的函数指针、唯一 v2 dispatcher。
- 字节/深度/节点预算、UTF-8/NUL、当前路径循环检测。
- GDB 原生/手动/自动模式、元数据校验、单次文本调用与故障隔离。
- runtime 内嵌脚本；消费方不需要 build.rs 或 Python 副本。
- 独立消费项目的默认关闭 feature，连同 a/b/c 的条件 derive 一起关闭；demo 本身始终启用。

旧 adapters、v1 runtime 入口、分页、LLDB/CodeLLDB 专用脚本与测试删除。历史版本在 Git 中可恢复；第一阶段验收记录不能当作 v2 测试证据。

## 2. 环境与复现

本地 Linux x86_64，GDB 17.1，nightly rustc `1.99.0-nightly (12c36e253 2026-08-10)`。关闭功能使用 stable rustc 1.97.1。nightly 滚动更新、其他 GDB/平台尚无普遍保证。

```sh
cargo fmt --all -- --check
cargo clippy --offline --workspace --all-targets --all-features -- -D warnings
cargo test --offline --workspace --all-features
python3 tests/compiler/run.py
python3 tests/integration/run.py --faults --lto --relocated
```

离线运行之前需 `cargo fetch --locked`。真实 GDB 测试需要 ptrace；runner 为各调试器子进程设置外部超时，并只回收自己创建的进程组。

## 4. 与当前 rust-gdb 的实际对照

当前工具链自带 pretty-printer，**标准 HashMap 并非完全不可用**，测试读到：

```text
HashMap(size=1) = {["points"] = Vec(size=2) = {core::option::Option<demo::Point>::Some(demo::Point {x: 1, y: 2}), core::option::Option<demo::Point>::None}}
```

dbgvis 对同一对象得到：

```text
{"points": [Some(Point { x: 1, y: 2 }), None]}
```

因此不能把“所有 rust-gdb 的 HashMap 都只显示内部布局”当作实测结论。收益在于由类型作者统一定义递归摘要、跨 crate 保留字段策略、不依赖调试器各版本对每个容器的专用展示能力。

当前自包含 AppState 的原生表示约 1500 字符（含内部对象结构和地址，随构建及类型名变化）；dbgvis 为：

```text
AppState { points: {"app": [Some(Point { x: 5, y: 6 })]}, bytes: b"hello world", ordered: {1: "one", 2: "two", 3: "three"}, address: 127.0.0.1:8080, state: State::Pending }
```

秘密字段未读取/展示。跨 crate 的无 Debug 递归单独由临时消费项目验证。hashbrown 仅加依赖和 register_type! 声明即输出 `{9: [8, 7]}`，未修改 runtime/Python 的类型逻辑。

## 5. 明确边界与后续工作

1. 自动缺失能力检查发生在代码生成阶段；metadata-only / cargo check 可通过。编译验收必须包含 cargo build。任意生命周期敏感的 specialization 不在承诺范围内。
2. LTO 可把不用的 enum 字段或整个局部值优化掉。初版测试因此被类型校验拒绝；没有放宽校验去猜测，示例改为给 checkpoint 传入活跃 AppState 引用以保证实测对象完整存活。无法恢复任意优化掉的业务值。
3. GDB 某些 Rust 动态类型只保留活动 enum 变体或省略尾部 padding；实现加入结构化 DWARF 核对。所有同名不同 crate 版本、所有调试信息形式仍未验收，类型元数据不是内存安全证明。
4. 编译 feature 关闭消除了独立消费项目依赖图中的 runtime，但启用后的 enable 有一次注册表分配。demo 始终启用；尚未系统测量 clean build/derive 成本、enable 耗时、100 次摘要或 128 个独立变量性能。
5. 安装 CLI setup/doctor/uninstall、完整 cargo package clean-room 发布演练、已有配置合并/卸载测试仍待实施。临时 path 消费项目和搬移二进制只证明接入/嵌入的一部分，不等价于已发布。
6. core dump、所有优化缺失值、重复加载/跨版本升级、所有 panic payload 行为与完整平台矩阵仍需扩充真实后端验收；核心已拒绝无执行能力目标。LLDB/CodeLLDB 和 v1 不在本轮交付中。
7. CI 已调整为 nightly/GDB，不能据此宣称远端 workflow 已运行或所有 CI 环境都支持相同 GDB 超时接口。

结论：已达到“实现核心并初步验证 HashMap、第三方 fmt 及泛型容忍度”的范围；Q4/Q5 中完整安装分发、性能与广泛兼容性验收尚未完成。
